Date: 2026-11-06. Owner: MANZUR-WEB-ORCHESTRATOR-01. This is a staged implementation plan, not a production-release claim.

## Verified baseline and boundaries
- Authorized parent rootIndex 6: `github.com/electrocicla/martial-arts-manager`, `feature/manzur-white-label-multitenant`, HEAD `357d41114374`, origin ahead 0 / behind 0 and clean at entry.
- `martial-arts-manager-native` inside the parent is a **separate ignored Git repository** with pre-existing modified/untracked accounting files. Read-only in this project; do not bundle into parent publication, build Android APKs, or alter either native package identity.
- Two existing native brand builds use distinct application IDs and shared D1 tenant routing; Manzur native may continue accessing `https://hamarr.cl/api` with its organization header. - Existing `wrangler.toml` references a production D1 ID; its actual remote schema/secret/binding state and Manzur bootstrap roles are **not verified**. No D1 writes, migrations, credential operations, production DNS edits, payment enablement or production Hamarr deployment in this implementation.

## Cascade impact and threat model
1. **Frontend tenant identity:** `src/lib/organization.ts` resolves the build-pinned `VITE_ORGANIZATION_ID`, and `src/lib/api-client.ts` injects `X-Organization-ID` and branch/token state. `src/context/AuthContext.tsx` manages same-origin HttpOnly refresh and per-organization session hints. Browser origin is a transport boundary, not independently sufficient membership authorization. Cross-tenant JWT claims and branch scopes must still be rejected server-side.
2. **Routes and branding:** `src/components/LandingPage.tsx`, `src/pages/{Login,Register}.tsx`, `src/App.tsx`, navigation, i18n, `index.html`, `public/{manifest.webmanifest,sw.js,offline.html,_headers}`, logo/favicon/meta/social image, `src/lib/registerServiceWorker.ts`, `src/components/mobile/AndroidApkInstallPrompt.tsx`. No HAMARR identity may leak into Manzur distributed static files, and no unapproved Manzur artwork may be represented as approved. Host-specific PWA caches and installation/deep-link policy must not cross brands; do not offer a HAMARR APK to Manzur visitors.
3. **Authentication/onboarding:** `functions/api/auth/{login,register,refresh,logout,me,pending-approvals}.ts`, `functions/middleware/auth.ts`, `functions/utils/{organizations,branches,jwt,db}.ts` and `src/lib/validation.ts`, `src/pages/Register.tsx`, `src/components/ui/InstructorSelect.tsx`. Current server accepts Manzur student registration without instructor, but frontend requires one for both brands. Align with server-authoritative organization policy, preserve HAMARR requirement and ensure instructor approval belongs to correct tenant/branch. Browser hostname-to-organization binding must be fail-closed on browser requests, while neutral/native transport must be evaluated independently without accepting forged platform headers as privileged identity.
4. **Data isolation:** `migrations/add_multi_tenant_organizations.sql`, `migrations/add_requested_instructor_to_memberships.sql`; `organizations`, `organization_memberships`, `platform_admins`, `users`, `branches`, `students`, `classes` (weekly generated children), `settings`, `payments`, `notifications`, `attendance_qr_codes` and related triggers. Existing migration is not idempotent; never auto-run. Shared users/global email and scoped memberships require negative proof that APIs cannot change org/branch through client headers or stale sessions. QR/class/weekly, analytics, student, staff and approval paths must continue scoped through the existing middleware/branch resolvers.
5. **Payments and integrations:** `functions/api/payments/mercadopago/{config,preference,webhook,status}.ts` and `functions/utils/mercadopago.ts`; config by owner/org/branch, metadata, signature, external references, redirect URLs and callbacks. Current preference accepts caller-provided URL fields or configuration, and derives defaults from request origin. Tighten untrusted redirect/payment URL boundaries and confirm webhook record lookups are tenant-scoped. Never execute live checkout or write real payment records during QA.
6. **Cloudflare and releases:** `package.json`, `vite.config.ts`, `wrangler.toml`, `scripts/post-deploy.mjs`, `.github/workflows/ci.yml`, `public/.well-known/assetlinks.json`. Produce deterministic, separately branded `dist` outputs using brand-pinned build targets, with distinct Manzur Pages+Functions project and same-origin `/api`, explicit D1/R2 bindings and secrets per project. Existing `deploy` points to HAMARR production and must remain unchanged until separately approved. Preview project/bindings require real Cloudflare evidence; no pretend Worker endpoint, no auto-migrations or prod binding copied into preview without owner authorization.
7. **Android compatibility:** Native separate repo brand catalog, `build:apk:hamarr`/`build:apk:manzur`, application IDs/deep links, `EXPO_PUBLIC_MANZUR_API_URL` and native `X-Client-Platform`. Source constraints only—no nested source edits, APK rebuild or package/signing in this checkpoint.

## Implementation order and independent ownership
- **WEB-A** — Own frontend branding only: typed branding catalog, LandingPage/Login/App and directly related visual shell, index/meta, PWA assets/manifest/cache, Android prompt and brand-specific UI unit tests. No auth backend or deployment scripts. Coordinate any dynamic index generation requirement with WEB-B without overlapping file edits.
- **WEB-B** — Own `package.json`, CI, `scripts/` web build/deploy validation and Cloudflare Pages config/docs/test scripts. Build both brands deterministically; make Manzur Pages project creation/deploy an explicitly guarded path, not a production side effect. Do not edit A's markup or service worker; coordinate required inputs.
- **WEB-C** — Own auth and browser host-binding backend paths, registration UI validation and tests, tenant/role/branch negative tests. Must preserve legitimate native transport and enforce server membership/JWT; never assume platform marker itself authenticates a request. Do not edit A's branding files. Browser Manzur hostname should only bind Manzur browser requests, with host strategy testable using pure functions.
- **WEB-D** — Own MercadoPago preference/redirect/webhook security and tests, R2 callback review; no live payments or D1 writes. Do not edit C's auth core. May start after C coordinates any shared host allowlist contract.
- **Orchestrator** — Own this plan, integration QA and documented readiness/rollback checklist; resolve cross-lane dependencies by messages rather than overlapping writes. Subagents deploy sequentially with verified connectedAt and disjoint claims, and commit/push only owned verified files. Git publication and shared heavy validation are serialized.

## Acceptance and verification
- Both `VITE_ORGANIZATION_ID=hamarr` and `=manzur` builds pass strict typecheck, lint, relevant Vitest suite and output contamination checks; static page titles, OG, manifest, PWA cache and install links reflect the correct tenant. HAMARR retains existing design and app route; Manzur requires modern visual identity without approved art inference.
- Browser on known Manzur host cannot masquerade as HAMARR and vice versa; unknown or mismatched browser host does not silently fall back to HAMARR. Existing native requests remain possible under normal JWT/membership security. Cross-tenant JWT/cookie/role/branch/QR/class/student/payment denial tests are explicit.
- Registration matches per-tenant policy; instructors/approvals scoped; callbacks and webhook storage validate signature plus tenant and branch. No bypass of Turnstile or security via forged client headers.
- Every implementing agent documents exact tests, owned files, scope-limited Git commit SHA/push, upstream ahead=behind=0, and final Agents Global disconnect. Orchestrator reruns integrated checks after merging agent edits, documents any failures.
- Preview only if Cloudflare project identity, safe non-prod D1/R2 bindings/secrets, and read-only authorization have been verified; otherwise state the concrete deployment gate. Production `manzurbros.cl` DNS/TLS/merchant, production D1/schema/admin provisioning, Turnstile/allowed origins and final smoke are explicitly owner-gated.

## Rollback
- Preserve the current HAMARR Pages project and `hamarr.cl` DNS untouched. For a bad Manzur preview, disable/remove the preview route or redeploy its last known-good artifact only after confirming project ownership; do not touch HAMARR production.
- Keep the parent branch's prior commit available; source rollback requires owner approval and normal forward correction (no force push, reset or automatic destructive revert). Use separate host-only cookies and versioned service-worker cache to prevent cross-domain bleed.
- No database migration or production payment mutation occurs in this checkpoint; rollback of schema is intentionally not part of this plan.
